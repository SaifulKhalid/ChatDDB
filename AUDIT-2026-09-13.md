## 1. Executive Summary

ChatDDB is a ChatGPT-style chat application that is **considerably more
sophisticated than its README, or the person maintaining it, probably realises**.

Its stated product is ordinary: sign in with Google, chat with an AI, attach
files, generate images. Its actual engineering achievement is different, and is
almost invisible from the user's side: it is a **database-driven multi-provider
AI aggregation platform**. Users pick a *brand* — "ChatGPT", "Claude", "Grok" —
from a menu. Behind that menu, a routing table decides which upstream gateway and
which upstream model actually answers, fails over silently when one is down, and
records health so a failing route is demoted automatically. Upstream model IDs,
provider identities, credentials, latency, and health are never sent to the
browser. That boundary is genuinely enforced in code, not just described in a
README.

The quality is **well above what the assignment assumed**. This is not the work
of someone guessing their way through. The code contains:

- A real security model (JWKS token verification with no service-account key,
  authorisation enforced by the type system rather than by convention).
- Deliberate, documented engineering around a hard platform limit (the Workers
  Free 10 ms CPU ceiling, which shapes PDF extraction and image handling).
- Honest inline commentary that reasons about *why*, including measured
  micro-benchmarks.
- A consistent house style: bound SQL parameters, "ownership is a WHERE clause,
  not a post-fetch check", server-authoritative conversation history.

The significant defects are **not** architectural. They are a small number of
**specific, fixable mistakes** — most notably a plaintext credential leak in the
admin API, a missing rate limit on that same API, and an SVG sanitisation bypass
in the fullscreen viewer. Alongside them sits a layer of **stale documentation
and dead code** that has accumulated because features were built faster than the
comments describing them were retired.

**Bottom line:** This is a **Functional-to-Advanced MVP with production-grade
instincts in several places**, held back from production-readiness by a handful
of concrete security defects and the absence of any automated regression safety
net. The distance to "production-ready" is measured in days of focused work, not
months.

## 2. What This Project Actually Is

**FACT — what the code does:**

A single Cloudflare Worker serves both a React single-page application and a
`/api/*` backend. It provides:

1. **Authentication** via Firebase (Google sign-in), verified server-side with
   Google's public JWKS. No Firebase Admin SDK, no service-account key anywhere
   in the project (`worker/auth/verify.ts:4-16`).
2. **Conversations** stored server-side in D1, with the server as the authority
   on history (`worker/db/messages.ts:1-20`).
3. **File attachments** (PNG, JPEG, WebP, PDF) stored in R2, validated by magic
   bytes, served back through HMAC-signed short-lived URLs.
4. **PDF understanding** — text extracted client-side with pdf.js, stored in R2,
   chunked, and injected into the prompt as delimited context.
5. **Image generation** on Cloudflare Workers AI (flux-1-schnell) with
   Pollinations as a backup.
6. **A dynamic multi-provider AI routing layer** — the heart of the system.
7. **An admin panel** for users, activity, files, and the AI routing
   configuration itself.
8. **SVG diagram generation** — the model can emit ```` ```svg ```` fences which
   are gated, sanitised, and rendered inline.

**INFERENCE — why it exists:**

The git history (48 commits) and the migrations tell a story of iterative
reinvention rather than a single design. The project appears to have begun as a
WhatsApp Cloud API webhook demo, become a multi-provider chatbot, been rewritten
onto Next.js, then rewritten again onto Vite + React 19 + a modular Worker at
`v1.0.0`. The current shape — hiding which AI actually answers — appears to be a
deliberate product decision taken late, not the original intent. Commit
`461eef4` ("feat: implement hidden multi-AI aggregation platform with failover")
and `92fa38b` ("Hide non-working and down AI models from user discovery") mark
that pivot.

**What makes it genuinely unusual:** the branded service names are a *presentation
layer over a routing table*. "ChatGPT" is not an API; it is a row in
`ai_services` that maps to one or more rows in `ai_routes`, each pointing at a
provider plus an upstream model ID. An administrator can re-point "ChatGPT" at a
completely different upstream model without any user-visible change. That is a
real architectural capability, and it is fully built.

## 3. Architecture Overview

```
Browser (React 19 SPA, from dist/)
   |  Firebase ID token (bearer)
   v
Cloudflare Worker  ── run_worker_first: ["/api/*"]
   |
   |-- worker/index.ts   ROUTES[] table, each with guard: 'public'|'user'|'admin'
   |-- auth/verify.ts    JWKS verification of the Firebase JWT
   |-- auth/middleware.ts requireAuth / requireAdmin -> AuthedContext
   |
   |-- routes/chat.ts     the core: SSE streaming chat
   |     |-- orchestrator.ts  candidate selection + failover
   |     |     |-- db/aiRouting.ts   services / routes / providers / health
   |     |     |-- adapters/openai.ts  OpenAI-compatible HTTP client
   |     |-- sse.ts       upstream frame -> client frame normalisation
   |     |-- lib/figureGate.ts  SVG fence buffering + sanitisation
   |
   |-- routes/images.ts   image generation (Workers AI -> Pollinations)
   |-- routes/files.ts    uploads, signed view URLs
   |-- routes/sessions.ts conversation CRUD
   |-- routes/admin*.ts   admin API
   |
   v
Cloudflare bindings
   D1 (SQLite)  ── users, sessions, messages, files, activity_logs,
                   rate_counters, ai_services, ai_routes, api_providers,
                   route_health
   R2           ── uploads, extracted PDF text, generated images
   Workers AI   ── flux-1-schnell image generation
```

**What it is:** a single deployable unit — one Worker, one D1 database, one R2
bucket — containing the entire product.

**Why it exists this way:** the Workers Free plan's 10 ms CPU ceiling and absence
of Queues/cron shaped much of the design. The comments are explicit that the
architecture is a response to that constraint, not a stylistic preference
(`worker/lib/files/pdf-client.ts:1-26`, `worker/db/files.ts:272-278`).

**What depends on what — the critical paths:**

| Component | Depends on | If removed |
|---|---|---|
| `routes/chat.ts` | orchestrator, adapters, sse, messages, sessions, aiRouting | The product ceases to exist; nothing else is the product |
| `orchestrator.ts` | aiRouting DB tables, adapters | Chat works for one provider only; all failover and the brand-hiding design collapse |
| `auth/*` | Firebase JWKS, `users` table | Every `/api/*` route except 5 public ones stops working |
| `db/client.ts` | — | Everything: it is the only SQL entry point |
| `lib/figureGate.ts` + `sanitizeSvg.ts` | sse.ts | SVG output is either unsanitised (**security**) or absent (**feature loss**) |
| `routes/images.ts` + `images.ts` | AI binding, R2 | Image generation and the `generate_image` tool both disappear |
| `lib/files/context.ts` | R2 extracted text | PDFs become unreadable attachments |
| `routes/adminAi.ts` | aiRouting | The routing table becomes editable only by SQL |

**The five public (unauthenticated) routes** are `/api/health`, `/api/ai-services`,
`/api/models`, `/api/auth/session`, `/api/files/view` (`worker/index.ts`). Everything
else requires a verified token and, for admin routes, an admin row.

## 6. What Is Fully Implemented

These are complete and coherent end-to-end: UI, API route, data layer, and audit.

**1. The authentication chain.** Token verification (`auth/verify.ts`) pins
issuer, audience, and algorithm; caches JWKS at module scope; allows 30 s clock
tolerance; rejects future `auth_time`. `requireAuth` re-reads the user row every
request so suspension is immediate rather than token-lifetime-delayed
(`middleware.ts:56-63`). This is genuinely well-built.

**2. The multi-provider routing layer.** `db/aiRouting.ts` (683 lines),
`orchestrator.ts`, and migration 0007 together form a complete CRUD + selection +
health system. Services, routes, providers, weights, priorities, capabilities,
per-route configuration, and circuit-breaker state are all real and all used.

**3. The public/private boundary.** `routes/services.ts` maps only
`{key, name, public_name, capabilities}` outward, explicitly commenting
`modelId: s.public_name, // Public name only, never raw upstream model`. The chat
route exposes only `X-ChatDDB-Model: service.public_name` (`chat.ts:457`). The
error classifier sanitises every message (`adapters/errors.ts`).

**4. File handling.** Magic-byte sniffing with extension cross-check, SVG
explicitly refused with a stated reason, size ceilings per type, row-first
write ordering so a crash never leaves an untracked R2 object, HMAC-signed
time-limited view URLs, `nosniff`, `Content-Disposition` differing by type, and
`CSP: default-src 'none'; sandbox` on served files. This is careful work.

**5. Image generation.** `images.ts` (618 lines) is thorough: provider chain,
separate crossable/non-crossable error policy (a prompt refusal does not cross
over to another provider — a deliberate and correct product decision), measured
base64 micro-benchmarks against the 10 ms CPU ceiling, and dedicated audit rows.

**6. Rate limiting.** `lib/ratelimit.ts` uses absolute window buckets (correct
given Workers pin `Date.now()` between I/O), counts-then-compares, and UPSERTs to
avoid read-then-write races. `max: 0` disables a window, which is a documented
operator escape hatch.

**7. Audit logging.** `activity_logs` is written from 18 distinct call sites, is
never deletable through any API, and hashes IPs rather than storing them.

## 7. What Is Partially Implemented

**1. SVG figure generation.** The pipeline — fence detection (`figureGate.ts`),
server sanitisation (`sanitizeSvg.ts`), client rendering (`SvgFigure.tsx`) — is
complete and well-reasoned. **But the fullscreen viewer bypasses the client-side
sanitisation** (see §11, SEC-3). The server-side allowlist still applies, so this
is defence-in-depth lost rather than a direct hole — but it is the *documented*
second layer, and it is off.

**2. The admin AI routing API.** Full CRUD exists and the UI is complete. Two
defects: it returns plaintext credentials on create/update (§11, SEC-1), and it
applies **no rate limiting at all** (§11, SEC-2), including on an endpoint that
makes sequential live upstream calls.

**3. PDF worker-side extraction.** Fully written, fully documented, and
deliberately disabled — the import is commented out and
`isWorkerExtractionAvailable()` returns `false`. This is honest engineering: the
upgrade path and its five steps are written out in the file header
(`pdf-worker.ts:11-25`).

**4. Data retention.** `prune.mjs` implements exactly the right policy — 90-day
activity, 2-day counters, 24-hour orphans, 30-day soft-deleted sessions — and
even documents why it must run `--json` and why it deletes cascade rows
manually. **But nothing schedules it.** The user-facing privacy page says
activity records are "pruned automatically" (`public/privacy.html:197`). They are
not; an operator has to run the command.

**5. Title provenance.** Migration 0005 adds `title_source IN
('placeholder','auto','manual')` and the columns are used correctly. But no code
path ever writes `'auto'` — `autoTitle()` is a synchronous clip of the user's own
first line (`chat.ts`), not a model-generated title. The client polls for ~33
seconds hoping the server will replace a placeholder (`ChatApp.tsx:454-478`,
`TITLE_POLL_DELAYS_MS`), which it never will.

**6. Soft delete.** Conversations are hidden, not removed, and this is disclosed
in the privacy page. Correct as designed; worth noting the disclosure is real.

## 8. Hidden / Underused Capabilities

Functionality that exists and works but is not surfaced, not used, or
under-appreciated:

1. **Administrators can completely re-point a brand at a different backend, live.**
   Add a provider, add a route, reorder priorities — no deploy. This is the single
   most powerful thing in the codebase and is essentially invisible.
2. **Weighted route distribution.** `ai_routes.weight` exists and is stored, but
   `resolveEligibleRoutes()` orders by priority; weights are not used to split
   traffic. Present, unused.
3. **Per-route `configuration`** (`tokenParam`, `maxOutputTokens`,
   `reasoningEffort`) is threaded all the way into the adapter
   (`adapters/types.ts:45-50`) but is only ever set by the seed migration.
4. **`hasDocuments`** is accepted as a parameter by `resolveEligibleRoutes()` and
   never used to filter — document-capable requests are not routed preferentially.
5. **Circuit breakers demote rather than drop** (`applyCircuitBreakers()`): a
   circuit-broken route stays in the candidate list at lower priority. This is a
   thoughtful choice nobody reading the code casually would notice.
6. **The audit log is a genuine operational asset.**
   `actionCounts`, `distinctIpsSince`, `countSince` support questions the admin UI
   does not yet ask (e.g. failover frequency per provider over time).
7. **The chunk boundaries are RAG-ready by design** (`context.ts:6-15`) — the
   structure needed for embeddings already exists. Nothing uses it yet.
8. **`GET /api/ai-services` is a complete public endpoint** that no frontend code
   calls. The UI still runs on the legacy `me.models` shape (see §13).

**Overall label: Functional MVP, trending Advanced MVP.**

It is well past "prototype" — the data model, the auth model, and the routing
layer are all deliberate and coherent. It is not yet "Production-Capable"
because of the security defects in §11 and the total absence of regression
testing. The distance is short.

**Size: surprisingly large relative to the apparent product.**

35 Worker modules, ~40 frontend modules, 7 migrations, 19 scripts — for a chat
app that presents itself as "a React chat application" in nine lines of README.
The routing layer alone (683 + 500 + 400 lines across three files) is larger than
many entire products. The ratio of engineering to visible surface is the single
most striking thing about this codebase.

## 10. Code Quality Assessment

**Genuinely strong.**

- **Consistent conventions.** Every DB module follows the same shape; every route
  takes an `AuthedContext`; every public mapper is named `toPublicX`. A new
  developer could follow it.
- **Commentary that explains *why*.** Examples that are unusually good:
  - `aiRouting.ts` — why untested routes are considered eligible.
  - `ratelimit.ts` — why absolute buckets (Workers pin `Date.now()`).
  - `sanitizeSvg.ts` — why attribute names are lowercased (HTMLRewriter
    pre-lowercases; `viewbox` vs `viewBox` is load-bearing).
  - `images.ts` — measured base64 decode timings (9.75 ms indexed-loop-invoked
    vs 0.33 ms inline) against the 10 ms ceiling.
  - `pdf-worker.ts` — the paid-plan upgrade path, step by step.
- **Security-conscious primitives.** `hmacVerify` uses `crypto.subtle.verify`
  for constant-time comparison. `ipHash` returns `undefined` rather than storing
  an unsalted hash when no salt is configured. `escapeLike` neutralises LIKE
  metacharacters. `sanitiseFilename` strips path components, leading dots, and
  bounds length.
- **Correct transactionality.** `db.batch()` used for message + counter + audit
  together; row-first write ordering in both upload and image paths.

**Weaknesses.**

- **Stale comments are a real pattern**, not isolated incidents. Several modules
  describe files, functions, or features that no longer exist (see §14). When the
  comments are this good, their being wrong is more dangerous than ordinary
  silence — a reader trusts them.
- **No automated tests.** The one unit-test file
  (`scripts/test-ai-orchestration.mjs`) is genuinely good — it imports worker
  sources directly and asserts on error classification, credential masking, and
  model-name sanitisation. But it is a script, not a suite: nothing runs it
  automatically, and nothing runs on commit or deploy.
- **Some very large files.** `chat.ts` (1144 lines), `sse.ts` (793),
  `AdminAiRouting.tsx` (1402), `adminAi.ts` (502). These are organised with clear
  section comments, but they are hard to hold in one head.
- **Lint configuration is nearly empty.** Three rules. It catches hook-rule
  violations and little else.

## 11. Security Assessment

**Nothing here was exploited.** Each item is a static observation with a severity
judgement and the reasoning behind it.

### SEC-1 — Plaintext credentials returned by the admin API · **HIGH**

`worker/routes/adminAi.ts` opens with:

> *"Secrets are masked (`••••••••1234`) and never returned in plaintext."*

That is true of `listAdminProviders` only. Both write paths return the raw row:

```
createAdminProvider  -> json({ provider: created }, 201, ...)
patchAdminProvider   -> json({ provider: updated }, 200, ...)
```

Both carry the `credentials` column in plaintext.

**Why it matters:** the admin frontend receives and holds a live provider API
key in application memory it has no use for. It widens the exposure surface of
the highest-value secret in the system to anything that can read the admin
browser's memory, and it contradicts the file's own documented contract — so a
future reader may trust the masked path without checking the write paths.
**Fix:** run both responses through the existing `maskCredentialsJson()`.

### SEC-2 — No rate limiting on the admin AI routing API · **HIGH**

Every route in `routes/admin.ts` calls `limitAdmin()`. **No route in
`adminAi.ts` calls it** — not create, not update, not delete, and not
`verifyAllRoutes`.

**Why it matters:** `verifyAllRoutes` makes **sequential live upstream calls
across every enabled route**. An admin session (or a compromised admin token)
can drive unbounded outbound requests to metered third-party gateways and
consume the shared neuron/credit budget. This is the one endpoint in the system
whose cost is proportional to the size of the routing table.
**Fix:** apply `limitAdmin()` to the mutating routes and give `verifyAllRoutes`
its own tighter action.

### SEC-3 — SVG sanitisation bypassed in the fullscreen viewer · **MEDIUM**

`src/components/SvgFigure.tsx` sanitises correctly on the inline path:

```ts
const fragment = DOMPurify.sanitize(source, {
  USE_PROFILES: { svg: true }, FORBID_TAGS, FORBID_ATTR, RETURN_DOM_FRAGMENT: true,
})
```

The fullscreen viewer does not:

```tsx
dangerouslySetInnerHTML={{ __html: source }}   // ~line 230
```

**Why it matters:** the design is explicitly double-layered — HTMLRewriter in the
Worker as the primary control, DOMPurify in the browser as defence in depth. This
disables the second layer. The server-side allowlist still stands, so a bypass
requires defeating HTMLRewriter first; but the code documents two layers and
delivers one.
**Fix:** render the already-sanitised fragment, or sanitise again before
`dangerouslySetInnerHTML`.

### SEC-4 — Email-clash sign-in merges identities unconditionally · **MEDIUM (conditional)**

`worker/db/users.ts:116-141`. When a verified token's `uid` is unknown but its
`email` matches an existing row, the code **overwrites that row's
`firebase_uid`** and returns it — inheriting its sessions, messages, files, and
any `role: 'admin'`. The comment says:

> *"that means the same person signed in through a different provider, which we
> surface rather than silently merging two identities."*

Nothing is surfaced. There is no log, no error, no confirmation — it merges
silently.

`emailVerified` is parsed from the token (`verify.ts:121`) and **never enforced**
— its only consumer writes it into an audit row (`routes/auth.ts:91`).

**Why it matters, precisely:** with Google-only sign-in (which the code asserts:
*"Google only, for now"*, `verify.ts:113`) every asserted email is
provider-verified and this branch is not reachable by an attacker. **If the
Email/Password provider is ever enabled in the Firebase console**, a registration
against a victim's address yields a token whose email matches, and the account —
including admin — transfers.
**Fix:** reject unverified emails (`if (!token.emailVerified) throw forbidden(...)`),
and at minimum log the merge.

### SEC-5 — Live production secrets in a plaintext file on disk · **MEDIUM**

`SECRETS.md` contains the real `FILE_URL_SECRET` (the HMAC key that mints file
view URLs) and `IP_HASH_SALT`, plus the exact `wrangler secret put` commands.

**Mitigating:** `.gitignore:21` lists `SECRETS.md`, and I confirmed the entry —
it is not committed. This is a local operational note, not a repository leak.
**Why it still matters:** `FILE_URL_SECRET` is the *only* thing protecting file
bytes. Anyone with read access to this machine (or a mis-scoped backup, or a
screen-share) can forge a view URL for any file ID, and the signed-URL design has
no second factor. It also cannot be rotated without invalidating nothing
(rotation is safe here, since URLs are 5-minute lived — but the doc does not say
so).
**Fix:** keep secrets in `.dev.vars` / the platform secret store only; if a local
record is needed, record *names* and rotation dates, not values.

### SEC-6 — CSP allows `'unsafe-inline'` scripts · **LOW-MEDIUM**

`public/_headers` includes `'unsafe-inline'` in `script-src`. It is required by
the theme bootstrap inline script in `index.html:10-18`, which must run before
first paint. The rest of the CSP is thoughtfully narrow (`frame-ancestors
'none'`, `base-uri 'none'`, an explicit `connect-src` for Firebase, and
`worker-src 'self' blob:` for pdf.js).
**Why it matters:** `'unsafe-inline'` neutralises a meaningful part of XSS
defence. The correct fix is a nonce or hash for that one script.

### SEC-7 — Stale third-party origins in the CSP · **LOW**

`font-src ... https://frontend-cdn.perplexity.ai` and
`img-src ... https://lh3.googleusercontent.com` remain from an earlier
Perplexity-era UI. The first is entirely unused (the codebase does not use
Perplexity). Each unused origin is unnecessary trust.
**Fix:** remove both, re-adding only what the app actually loads.

### SEC-8 — Seeded provider header impersonates a first-party CLI · **LOW (but note it)**

Migration 0007 seeds `prov-agentrouter` with a static header set:

```
User-Agent: claude-cli/2.1.158 (external, sdk-cli)
X-App: cli
```

**Why it matters:** this is not a security hole in ChatDDB; it is a
misrepresentation to the upstream gateway, and it is disclosed in the migration
where anyone can read it. I flag it because it is a product-integrity question,
not because it is an exploit. Combined with SEC-9, the system is already
presenting itself as something it is not.

### SEC-9 — Fail-open health default · **LOW**

`computeServiceStatus()` in `db/aiRouting.ts` treats an untested route as
healthy: `if (!r.health) return true`. **Why it matters:** "live" means "not yet
proven broken." A newly added route is advertised to users before it has ever
succeeded. This is a defensible trade-off (it prevents a cold start from hiding
everything) but should be a conscious one — a route could be probed once before
publication.

### Security strengths worth recording

- No service-account key exists in the project; only public key material is
  fetched. There is no admin private key to leak.
- `requireAuth` re-reads role and status per request, so suspension is immediate.
- Route guards are enforced by the type system — a handler cannot obtain
  `ctx.user` without passing through `requireAuth`/`requireAdmin`.
- SQL is always parameterised; table/column text comes from fixed maps.
- Error output is sanitised centrally; a probe learns nothing from a rejection.
- `/api/files/view` treats the signature as the capability, delivers
  `nosniff`, forces PDFs to `attachment`, and scopes caching to the signature's
  5-minute life.
- Bearer-only auth means no ambient credentials, so classic CSRF does not apply.

## 12. Reliability Assessment

**Strengths**

- **Failover is real and tested.** `adapters/errors.ts` classifies upstream
  failures into crossable and terminal; the orchestrator walks candidates and
  records health fire-and-forget. `scripts/test-ai-orchestration.mjs` asserts
  this behaviour.
- **Atomic batch writes.** Message + session counter + audit row + file links go
  down together or not at all.
- **Row-first storage ordering.** A crash between the DB row and the R2 put
  leaves a prunable row, never an untracked object.
- **Audit writes never throw.** `activity.log()` swallows its own failures so a
  logging problem cannot fail the request that triggered it.
- **The SSE parser guards a real production bug.** `parseChunk()` refuses
  `JSON.parse('null')` because AgentRouter emits a literal `data: null` for one
  model — a bug that was found in production and defended against in code.
- **Tool-call lookahead** (`LOOKAHEAD_FRAMES = 16`) exists because a simpler rule
  lost tool calls on 29% of image-intent turns. That number implies measurement.

**Weaknesses**

- **No automated regression protection.** A refactor that breaks failover,
  sanitisation, or SSE parsing will be caught by a human reading the diff, or by
  a user. There is no third option.
- **No scheduled maintenance.** Retention, counter cleanup, and orphan removal
  all require an operator to remember.
- **`getMe` is heavy.** The app's initial-load endpoint performs
  `listLiveServices()` (itself four D1 queries), `usageFor` (five more), and two
  rate-limit peeks — roughly 7–8 round trips before the client can render.
- **Silent degradation is the design.** By intent, a user never learns that their
  "ChatGPT" answer came from a different provider. That is a product decision,
  but it means failures are only visible in the audit log.
- **No alerting.** Nothing pages anyone when a provider dies or the neuron
  budget runs out.

## 13. Technical Debt

**CRITICAL** — security or correctness defects that should be fixed before wider
exposure:

1. Plaintext provider credentials returned by admin write endpoints (SEC-1).
2. No rate limiting anywhere in `adminAi.ts`, including `verifyAllRoutes` (SEC-2).
3. `dangerouslySetInnerHTML` on unsanitised SVG in the fullscreen viewer (SEC-3).

**HIGH** — actively misleading or distinctly risky:

4. `emailVerified` is parsed and never enforced, and the email-clash path merges
   accounts silently against its own comment (SEC-4).
5. `worker/failover.ts` is referenced five times in `images.ts`
   (`resolveProviders`, `completeWithFailover`, `FALLBACK_TIMEOUT_MS`) and **does
   not exist**. The file was removed in `05e332d` ("remove obsolete AI routing
   artifacts"). The comments describe a mechanism the code no longer has.
6. `lib/api.ts:85-86` reads `X-ChatDDB-Upstream` and
   `X-ChatDDB-Upstream-Model` — headers **nothing sets**, not even in the CORS
   expose list. Any client logic depending on them is dead.
7. `listLiveServices()` runs four queries on every call, and it is called from
   `getMe` on every app load. The canonical replacement endpoint
   (`/api/ai-services`) already exists — and `listAiServices()` in `api.ts:215`,
   the client helper for it, **is imported by no component**. The UI still runs
   the legacy `me.models` path. Two competing representations of the same data
   are maintained in parallel.

**MEDIUM** — real cost, not immediately dangerous:

8. `privacy.html:197-198` states activity records are "pruned automatically" at
   90 days and incomplete uploads are "cleared after 24 hours". `prune.mjs`
   implements exactly those windows but **nothing schedules it**. The stated
   policy and the deployed behaviour differ.
9. `refreshTitleIfPlaceholder` polls for ~33 seconds
   (`TITLE_POLL_DELAYS_MS = [1200, 2500, 5000, 9000, 15000]`) waiting for the
   server to generate a title. `autoTitle()` is a synchronous clip of the user's
   own first line and never writes `title_source: 'auto'`. The client is waiting
   for a feature that does not exist.
10. `getAdapter()` in `orchestrator.ts` handles **only** `case 'openai': default:`.
    A provider row with `adapter: 'workersai'` or `'pollinations'` silently gets
    the OpenAI adapter rather than an error.
11. `testConnection()` falls back to probing a hardcoded `'gpt-4o-mini'` — a
    model unrelated to this catalogue.
12. `resolveProviderCredentials()` (`orchestrator.ts:324`) prefers DB credentials
    and falls back to env vars **hardcoded to exactly two provider keys**
    (`codecraft`, `agentrouter`). Any provider added through the admin UI can
    therefore only ever store its key in D1 plaintext.
13. `toPublicModelKey()` (`db/messages.ts:50-60`) classifies by substring, and
    `includes('sol')` maps any id containing those three letters to "ChatGPT".
    Currently harmless — `model_used` stores the public name, and the fourth
    parameter `_upstreamModelId` is unused (`chat.ts:1060`) — but it is a latent
    mislabelling bug the moment anything stores an upstream id.
14. `documents` and `tools` capability checks default to **true**
    (`routes/auth.ts`): `caps.documents !== false`, `caps.tools !== false`, while
    `vision` defaults to false. Asymmetric and unexplained.
15. `resolveEligibleRoutes()` accepts `hasDocuments` and never filters on it.
16. `ai_routes.weight` is stored and never used for distribution.

**LOW** — cosmetic, or clutter that misleads a reader:

17. Stale document references: `PRIVACY.md` (migration 0002, `admin.ts:21`,

19. `ratelimit.ts:22` claims "`sample` exists for the high-frequency actions" —

20. An orphan doc comment with no function beneath it at `sse.ts:785`.

## 15. Architecture Strengths

1. **One deployable unit.** No service mesh, no queue, no external database to
   coordinate. Deployment is `wrangler deploy`.
2. **The routing layer is properly factored.** Configuration (D1), selection
   (orchestrator), transport (adapter), and health (circuit breakers) are
   separate concerns with clean seams. Adding a new *style* of provider means one
   new adapter, not changes throughout.
3. **Authorisation is structural, not procedural.** `guard: 'public'|'user'|'admin'`
   in a single table, and a context type that cannot be forged. This is the single
   best design decision in the codebase — it makes a whole class of bug
   unrepresentable.
4. **The public/private boundary is enforced, not documented.** A future
   contributor cannot leak an upstream model ID through the chat path without
   deliberately editing code that says, in the line above, that it must not.
5. **Server-authoritative history.** The client cannot inject a fabricated
   conversation into context; the server rebuilds it from D1 with both row and
   character caps.
6. **Constraint-driven design.** The Free-plan CPU ceiling is not fought or
   ignored — it is measured, documented, and designed around, with a written
   upgrade path.
7. **Defence in depth where it counts.** SVG sanitised twice, files validated by
   bytes, cache scoped to signature life, `nosniff` everywhere it matters.

---

## 16. Architecture Weaknesses

1. **The Worker is the whole product, with no seam for growth.** Chat, images,
   files, admin, and auth are one Worker. Fine now; it means any long-running
   work must fit the same CPU budget.
2. **No abstraction over D1 access patterns for read-heavy endpoints.** `getMe`
   fans out to 7–8 queries on every load with no caching or aggregation endpoint.
3. **Two representations of "the model list"** (`me.models` and
   `/api/ai-services`) are maintained in parallel, with the newer one unused.
   This is the kind of split that becomes permanent by accident.
4. **Health is inferred, not verified.** Untested routes are advertised as
   eligible, so the first user of a new route is the probe.
5. **No background execution.** No cron, no queues — so retention, orphan
   cleanup, and provider health probing all depend on a human.
6. **Adapter selection has no failure mode.** An unknown `adapter` value
   silently becomes OpenAI, which will fail confusingly rather than loudly.
7. **The audit trail is write-only in practice.** Rich data is collected; no
   operational dashboard or alert consumes it.
8. **The frontend's model surface is behind the backend's.** The server knows
   about services, capabilities, and routing; the client still thinks in terms of
   a flat legacy model list.

## 17. Current Limitations

**Functional**
- No conversation export, no account self-deletion, no admin user deletion.
- One tool only (`generate_image`).
- PDF text is client-extracted, so a user can supply text that does not match
  their document (bounded: it affects only their own conversation and logs, and
  the original PDF is retained as the authority).
- Worker-side PDF extraction is off until the paid plan is enabled.
- Document relevance is lexical term-overlap, not semantic.
- Image generation draws on a **shared, account-wide** neuron allowance
  (~173 images/day for the entire deployment, per the wrangler comments).

**Operational**
- Retention and cleanup are manual.
- No monitoring, alerting, or dashboards.
- No staged rollback, no canary, no feature flags.

**Quality**
- No automated test run on commit or deploy.
- Lint coverage is minimal.
- Sequential live-upstream calls (`verifyAllRoutes`) are unbounded per session.

**Product**
- Branded names do not match upstream identity. Migration 0007 routes "Grok" to
  upstream `gpt-5.6-sol`, and makes `deepseek-v4-flash` the priority-2 fallback
  for ChatGPT, Gemini, Claude, *and* Grok. A user who selects "Claude" and
  receives a DeepSeek answer is told nothing. This is the deliberate design, and
  I am not calling it a bug — but it is a limitation with a **truthfulness
  dimension** that a reader of the UI would not guess, and it deserves to be a
  conscious decision rather than an emergent one.

## 18. What Could Realistically Be Built From This Foundation

**Low effort (days) — because the hard part already exists**

1. **A working route-health dashboard.** The data exists in `route_health`;
   `getAdminAiHealth` already aggregates it. Only presentation is missing.
2. **Automatic provider probing on a schedule.** Requires the paid plan for cron,
   or an external trigger hitting an endpoint that already exists.
3. **Real model-generated titles.** `title_source: 'auto'` is reserved, the
   client already polls for it, and the routing layer can already make the call.
   The work is one server function.
4. **Conversation export.** Every piece exists: sessions, messages, files,
   signed URLs. It is an assembly job.
5. **Fix the plaintext credential leak and add `limitAdmin()`.** Hours, not days.

**Medium effort (weeks)**

6. **Retrieval with embeddings.** The chunk boundaries are already cut for it.
   `file_chunks` + an embedding call + a similarity query — a real RAG upgrade
   from a design that anticipated it.
7. **A second adapter family** (Anthropic Messages API, or a non-OpenAI-compatible
   gateway). The `ProviderAdapter` interface is clean and waiting.
8. **Weighted traffic distribution.** `ai_routes.weight` is stored and unused;
   A/B comparison of providers is a small change to `resolveEligibleRoutes()`.
9. **A genuine test suite.** The existing `.mjs` scripts are good raw material;
   the gap is a runner and a CI hook.

**High effort (months) — but structurally plausible**

10. **A multi-tenant version.** The routing layer already separates *what the
    user picks* from *what actually serves*, per deployment. Extending that to
    per-organisation routing and budgets is a change of scope, not of shape.
11. **An API product.** The public/private boundary, capability flags, per-key
    rate limiting, and audit trail are the components an API product needs. The
    current Worker is already, in effect, an internal API.

**What would be a rewrite, not an extension:** real-time collaboration, voice,
or anything requiring long-running background compute on the Free plan.

## 20. Final Verdict — How Much Has Actually Been Built?

**Substantially more than the product description implies, and more than the
assignment's premise assumed.**

This is not a prototype that happens to work. It is a **coherent system with a
real architecture**, and the parts that matter most are the parts you cannot see
from the outside.

The visible product is a chat app. The actual engineering is a **database-driven
multi-provider AI aggregation platform** with failover, circuit breakers, health
tracking, a genuine public/private boundary, and an admin surface capable of
re-pointing a brand at a different backend without a deploy. That layer is fully
built, correctly factored, and completely hidden from the user by design.

The security design is better than most production applications I would expect to
find at this stage: no service-account key anywhere, JWKS verification with
issuer/audience/algorithm pinning, authorisation enforced by the type system
rather than by convention, per-request role re-reads so suspension is immediate,
signed file URLs, and centrally sanitised errors. The commentary is
exceptional — it explains *why*, cites measured timings, and documents a
paid-plan upgrade path step by step. Whoever wrote this reasons carefully about
hard constraints; the Workers Free 10 ms CPU ceiling is not fought, it is
measured and designed around.

**Why the verdict is not higher.** Three defects are concrete and should be fixed
before this is exposed to more people: the admin API returns plaintext provider
credentials while its own header claims it never does; the same API has no rate
limiting at all, on an endpoint that makes sequential live upstream calls; and
the fullscreen SVG viewer disables the documented second layer of sanitisation.
Alongside them sits a layer of stale documentation — a referenced file that does
not exist, headers nothing sets, a client polling 33 seconds for a feature that
was never written, a privacy policy promising automatic pruning that is manual —
which is more dangerous here than usual *because* the comments are otherwise so
trustworthy. And there is no automated test net at all: one good unit-test file
that nothing runs.

**Why the verdict is not lower.** None of those are architectural. Every one is a
bounded, specific fix. The foundations — the routing layer, the auth model, the
data layer, the file pipeline, the error classifier — are sound, deliberate, and
in several places better than they need to be for a project at this stage.

**The honest summary:** a **Functional-to-Advanced MVP with production-grade
instincts and three production-grade holes.** The distance to "production-ready"
is days of focused work on the security items, plus the discipline to add a test
runner so the next change does not quietly undo what already works. The
foundation can carry far more than is currently built on it.
